# Sovereign CPA Engine — Complete Architecture

## System Definition

A financial close infrastructure that ingests general ledger data and produces certified, auditor-ready financial statements. The system replaces the manual Excel-based close process for PE-backed mid-market companies ($100M–$1B revenue).

**Core promise:** Plug in your GL → get certified financial statements you can trust without blinking.

**Fundamental constraint:** AI never touches numbers. All dollar amounts are computed by deterministic code. AI operates exclusively on text, classification, and pattern recognition in a strictly advisory capacity.

---

## 1. Architectural Principles

### 1.1 The Two Type Systems

Every value in the system is one of two types. These types are enforced at the database, API, and UI layers.

**Deterministic Values**
- Computed by arithmetic functions or sourced directly from GL import
- Stored in financial data tables
- Used in trial balances, financial statements, reconciliations, adjusting entries
- Participate in certification
- Traceable: every number can be followed back to its source through an unbroken chain of deterministic operations

**Advisory Values**
- Generated by AI models
- Stored in separate `ai_*` tables with no foreign keys into financial tables
- Never used as input to any computation
- Never appear on any financial statement
- Always displayed in visually distinct UI containers
- Exist solely to help humans work faster

These types never cross. There is no code path where an AI-generated number flows into a financial calculation.

### 1.2 The Handoff Pattern

Wherever AI assists a human who then provides input to the financial system:

1. **AI suggests** → writes to `ai_*` table only
2. **Human reviews** → sees suggestion displayed separately from financial data
3. **Human enters or confirms** → types or explicitly approves the value
4. **Deterministic processing** → system computes all downstream effects

The value stored in the financial table is attributed to the human, not the AI. Even if the human accepts the AI's suggestion unchanged, the system records it as a human-entered value.

### 1.3 The Cascade Principle

Every correction ripples through the entire close instantly:

- AJE posted → adjusted TB recalculates → affected reconciliations recalculate → statements marked stale → validation checks re-run → dashboard updates → issues auto-resolve or new issues created

This is not a batch process. It executes synchronously after every state change. The user always sees current data.

### 1.4 Decimal Precision

All dollar amounts use `Decimal.js` (or equivalent arbitrary-precision library). Native floating-point arithmetic is prohibited. `0.1 + 0.2` must equal `0.3`, not `0.30000000000000004`. A one-cent rounding error on a balance sheet is a system failure.

## 3. The Close Flow — Six Phases

### Phase 0: Pre-Close (Days 1–2 after period end)

**Purpose:** Establish a stable starting point by locking the period.

**Steps:**
1. Confirm period end date
2. Issue cutoff notice to AP, AR, Payroll, Fixed Assets
3. Wait for final subledger postings
4. Lock subledgers one by one as each confirms completion
5. Lock the general ledger for the period
6. Extract trial balance from GL

**Gate to proceed:** GL is locked. TB is extracted.

**What breaks:** Late invoices, payroll corrections, entries posted after cutoff, TB extracted before final posting.

**HITL resolution:** System enforces lockout sequencing. If TB extracted before lock, system flags and requires re-extraction after lock is confirmed.

---

### Phase 1: Ingest and Validate (Days 2–3)

**Purpose:** Get clean, mapped data into the system.

**Steps:**
1. Ingest trial balance (CSV/Excel/API)
2. Match every account to COA mapping
3. Run structural validation:
   - Total debits = Total credits → hard stop if fails
   - All accounts mapped → blocking if unmapped accounts exist
   - New accounts flagged → mapping required before proceeding
   - Contra-type balances detected → acknowledgment required
   - Period-over-period comparison → material changes flagged for later explanation
4. TB accepted, timestamped, hashed, immutable snapshot created

**Gate to proceed:** TB in balance, all accounts mapped, all structural issues resolved or acknowledged.

**What breaks:**
- TB doesn't balance → re-export required (no override possible)
- Unmapped accounts → AI suggests mappings, human approves
- Unusual balances → human acknowledges with justification or creates correcting AJE
- New accounts mid-period → mapping required before statements can generate

**HITL resolution for each:**

| Issue | Severity | Resolution Options |
|-------|----------|--------------------|
| TB imbalance | Critical | Re-export only. No override. Compare to prior period to identify discrepancy. |
| Unmapped account | Blocking | Accept AI mapping suggestion, map manually, or mark inactive (requires AJE to zero balance first) |
| Contra-type balance | Warning | Acknowledge with explanation, create correcting AJE, or investigate transaction detail |
| Material variance | Info (now), Blocking (at certification) | Explain now or defer to review phase |

---

### Phase 2: Account Reconciliation (Days 3–7)

**Purpose:** Prove that key balance sheet balances are real.

**Steps (per account):**
1. System presents GL balance (pulled from adjusted TB)
2. Human enters supporting balance (bank statement, subledger, schedule)
3. System computes variance (deterministic: GL − supporting)
4. If within tolerance → auto-approved
5. If outside tolerance → reconciling items required
6. Human adds reconciling items until variance is explained
7. Items requiring booking → system creates draft AJEs inline
8. Preparer signs off, reviewer approves

**Accounts requiring reconciliation:** All balance sheet accounts above a configurable materiality threshold. At minimum: cash, AR, AP, inventory, prepaids, accrued liabilities, debt, equity.

**Gate to proceed:** All required reconciliations complete and within tolerance (or variance explained and approved).

**What breaks:**
- Variance outside tolerance → add reconciling items or create correcting AJEs
- Subledger doesn't match GL → investigate JEs posted directly to GL bypassing subledger, create correcting AJE
- Items needing booking discovered during recon (bank fees, interest) → system creates draft AJE linked to the recon

**HITL resolution:** All resolution happens within the system. Reconciling items are added inline. AJEs are created directly from the reconciliation screen. When an AJE posts, the reconciliation auto-recalculates (cascade principle).

---

### Phase 3: Adjusting Journal Entries (Days 3–7, parallel with Phase 2)

**Purpose:** Correct errors, record accruals, and ensure completeness.

**Three categories of AJEs:**

**Recurring (system-proposed):** Depreciation, amortization, monthly accruals, prepaid amortization, deferred revenue recognition. System proposes from templates with amounts from schedules or prior period. Controller reviews and approves.

**Correcting (manual, discovered during reconciliation):** Reclassifications, error corrections, cutoff adjustments. Must reference the original entry being corrected. Must document what was wrong and why.

**Non-recurring (manual, unusual events):** Impairments, write-offs, restructuring, legal accruals. Require detailed memo, supporting documentation, and senior approval.

**Every AJE requires:**
- Debits = Credits (system-enforced, cannot save otherwise)
- All accounts are valid mapped accounts
- Memo/description (system-enforced, field is required)
- Preparer recorded automatically
- Approver required above configurable dollar threshold
- Immutable once posted (timestamped, hashed)

**Gate to proceed:** All recurring templates either posted or explicitly waived with documented reason.

**What breaks:**
- Recurring entry forgotten → system detects unposted templates, presents with prior amounts, user posts or waives
- Entry exceeds approval threshold → routed to approver, blocks until approved or rejected
- Insufficient documentation → system enforces required fields, non-recurring entries require supporting docs

**HITL resolution:** AJE workbench handles creation, approval routing, rejection with comments, and resubmission. Every action is within the system with full audit trail.

---

### Phase 4: Financial Statement Generation (Days 7–8)

**Purpose:** Transform the adjusted trial balance into four financial statements.

**This phase is entirely deterministic. No human judgment. No AI involvement.**

**Sequence:**
1. Generate adjusted trial balance (starting TB + all posted AJEs)
2. Generate Income Statement (aggregate period activity by mapped reporting line items, compute subtotals)
3. Generate Balance Sheet (aggregate ending balances by mapped reporting line items, compute totals)
4. Generate Statement of Stockholders' Equity (rollforward from prior period)
5. Generate Cash Flow Statement — indirect method (net income + non-cash adjustments + working capital changes + investing + financing)
6. Run cross-statement integrity validation

**Hard checks (must all pass):**
- Total debits = Total credits in adjusted TB
- Total Assets = Total Liabilities + Total Equity
- Net Income ties across IS, equity rollforward, and CF starting point
- Ending cash on CF statement = cash on balance sheet
- Every balance sheet account change is classified in the CF statement
- Retained earnings movement = Net Income − Dividends

**If any hard check fails:** Statements are not presented. System runs diagnostics to identify the cause (mapping errors, unclassified accounts, double-mapped accounts). User fixes the issue through the HITL system and statements regenerate.

**What breaks:**
- BS doesn't balance → mapping error. System identifies which account is mapped to wrong statement type. User corrects mapping, statements regenerate.
- CF doesn't reconcile → unclassified balance sheet change. System identifies which account's change is missing from the CF. User sets the cash flow classification, statements regenerate.
- CF requires split classification (e.g., PP&E has both depreciation and capex) → system detects from AJEs and presents split for user confirmation.

---

### Phase 5: Review and Variance Analysis (Days 8–10)

**Purpose:** A senior person reviews the statements and confirms they make sense.

**Steps:**
1. Period-over-period flux analysis for every material line item
2. AI drafts variance explanations (using only system-computed numbers as inputs — AI does not calculate, it only assembles sentences from pre-computed values)
3. Controller reviews, edits, approves each explanation
4. Analytical review — system computes key ratios and flags anomalies
5. Senior reviewer examines complete package
6. Reviewer approves, rejects with comments, or requests information

**Gate to proceed:** All material variances explained. Reviewer approved.

**HITL resolution:** All variance explanations are written/edited within the system. If reviewer rejects, specific comments route back to the preparer. The close status returns to IN_PROGRESS for corrections, then re-advances to UNDER_REVIEW.

---

### Phase 6: Certification and Lock (Days 10–12)

**Purpose:** An authorized person formally certifies the close.

**Pre-certification checklist (all must be TRUE):**
- [ ] Trial balance in balance
- [ ] All accounts mapped
- [ ] All required reconciliations complete and within tolerance
- [ ] All recurring AJEs posted or waived
- [ ] A = L + E
- [ ] Net income ties across all statements
- [ ] Cash ties between CF and BS
- [ ] All material variances explained
- [ ] Senior reviewer approved

**Certification action:** Authorized user clicks "Certify." System records who, when, hash of complete financial statement package, and state of every validation check at the moment of certification.

**Output:** Immutable close package containing four financial statements, adjusted trial balance, AJE summary, reconciliation summary, variance analysis with explanations, and certification record.

**Period locks.** Any future correction requires explicit reopen by an authorized user, documented reason, full audit trail, and resets certification.

## 4. The Close Orchestrator (State Machine)

```
OPEN → IN_PROGRESS → UNDER_REVIEW → CERTIFIED → LOCKED
```

| Transition | Requirements |
|---|---|
| OPEN → IN_PROGRESS | Authorized user initiates close |
| IN_PROGRESS → UNDER_REVIEW | TB validated, all accounts mapped, all recons complete, all recurring AJEs posted/waived, statements generated, all hard checks passing, all material variances explained |
| UNDER_REVIEW → IN_PROGRESS | Reviewer rejects (preserves all work) |
| UNDER_REVIEW → CERTIFIED | All prior requirements still met + reviewer approved + certifier authorized |
| CERTIFIED → IN_PROGRESS | Authorized reopen with documented reason (rare, painful by design) |
| CERTIFIED → LOCKED | Configurable time period elapsed or manual trigger (permanent, irreversible) |

The state machine enforces that no step is skipped. If any requirement for a transition is unmet, the system shows exactly what's missing.

## 5. The HITL Issue Resolution System

Every problem the system detects becomes a first-class Issue object with a lifecycle:

```
DETECTED → ASSIGNED → IN_PROGRESS → RESOLVED → VERIFIED
```

### Issue Severity Levels

| Severity | Meaning | Effect |
|---|---|---|
| Critical | System error (e.g., BS doesn't balance after generation) | Cannot proceed at all. Immediate diagnostic. |
| Blocking | Must resolve before certification | Work can continue, but cannot certify until resolved. |
| Warning | Requires acknowledgment | Must acknowledge with justification; doesn't block work. |
| Info | Awareness only | Surfaced for review; no action required. |

### Resolution Types

| Resolution | Description |
|---|---|
| AJE posted | A correcting or reclassifying entry was created and posted |
| Mapping corrected | An account mapping was fixed |
| Re-ingested | The TB was re-exported from GL and re-imported |
| Reconciling items added | Variance explained by outstanding items |
| Acknowledged with justification | Issue accepted as-is with documented reason |
| Classification updated | Cash flow or account classification was set or corrected |
| Escalated and resolved | Assigned to senior user who resolved it |

### Key Design Principle

Every resolution happens within the system. The user never leaves the application to fix something. If a reconciliation reveals a GL error, the user creates the correcting AJE directly from the reconciliation screen. If a mapping is wrong, the user fixes it from the statement generation diagnostic. Every fix triggers the cascade — recalculating all downstream data instantly.

## 6. AI Boundaries — Precise Specification

### What AI Does

| Function | Input (read-only) | Output | Touches Numbers? |
|---|---|---|---|
| COA mapping suggestions | Account code, name, type | Suggested reporting line item + confidence | No. Classification only. |
| Variance explanation drafts | Pre-computed amounts, account details | Text narrative | References system-computed numbers. Does not compute. |
| Anomaly detection | Current and historical TB data | Text flags ("this looks unusual") | Reads numbers. Outputs text only. |
| AJE suggestions | Account balances, prior entries, templates | Suggested entry (accounts + memo) | Suggests amounts, but these never auto-post. Human must enter/confirm every dollar. |
| Close timeline prediction | Historical close data, current progress | Estimated completion dates | Predicts dates, not financial amounts. |
| Intelligent Q&A | Full close dataset | Natural language answers | References numbers. Does not compute. |

### What AI Never Does

- Compute any dollar amount
- Post any journal entry
- Modify any trial balance
- Generate any financial statement line item
- Pre-populate any financial input field (suggestions displayed separately; user must explicitly act)
- Participate in any certification decision
- Write to any financial data table

### Database Enforcement

AI has READ access to financial tables. AI has WRITE access only to `ai_*` tables. There is no database permission, no API endpoint, and no code path that allows AI output to directly enter a financial table.

### UI Enforcement

AI-generated content always appears in a visually distinct container (different background, labeled with "AI Suggestion"). AI-suggested numbers are displayed as approximations ("~$45,200") and never pre-filled into financial input fields. Financial statement numbers never carry an AI badge and always drill down to deterministic source data.

## 7. The Certification Guarantee

When the system certifies a close, this statement is architecturally true:

> Every dollar amount on the enclosed financial statements was computed by deterministic arithmetic operations applied to data sourced from the general ledger and human-approved adjusting journal entries.
>
> No dollar amount on any financial statement was generated, estimated, or influenced by any artificial intelligence model, machine learning system, or probabilistic algorithm.
>
> AI was used in an advisory capacity for: suggesting account classification mappings (human-approved), drafting variance explanation narratives (human-reviewed), and flagging unusual patterns for human review. All AI-assisted outputs were subject to human review and approval before any related action was taken.

## 9. Validation Engine — Complete Check Registry

### Hard Checks (block certification)

| Check | What It Validates |
|---|---|
| TB Balance | Sum of all debits = sum of all credits |
| Mapping Completeness | Every account with a balance is mapped to a reporting line item |
| Balance Sheet Equation | Total Assets = Total Liabilities + Total Equity |
| Net Income Tie | IS net income = equity rollforward net income = CF starting net income |
| Cash Tie | CF ending cash = BS cash line |
| CF Completeness | Every BS account change is classified in the CF statement |
| Retained Earnings Tie | RE ending = RE beginning + net income − dividends |
| Recon Completeness | All required reconciliations are complete and within tolerance |
| AJE Completeness | All recurring templates posted or waived |
| Variance Explanations | All material line item variances have approved explanations |
| Reviewer Approval | Senior reviewer has signed off |

### Soft Checks (warnings, don't block)

| Check | What It Flags |
|---|---|
| Contra Balances | Asset accounts with credit balances or liability accounts with debit balances |
| Flux Thresholds | Line items with period-over-period changes exceeding configurable thresholds |
| Ratio Anomalies | Key ratios outside historical norms or industry benchmarks |
| Round Number Entries | Suspiciously round amounts in accounts that normally have precise amounts |
| Duplicate Detection | Same account, amount, counterparty within N days |
| Unapproved AJEs | Entries above threshold without approver sign-off |
| Thin Explanations | Reconciliation variance explanations that are very short or generic |

## 10. Statement Generator — Deterministic Computation Core

These are the only functions that compute dollar amounts. They are pure arithmetic. They total roughly 200 lines of actual computation code.

| Function | Input | Output | Operation |
|---|---|---|---|
| `sumBalances` | Account list | Net balance | Sum debits, sum credits, return net |
| `computeVariance` | Current, prior | Amount + percentage | Subtraction and division |
| `validateDebitsEqualCredits` | AJE lines | Boolean | Sum debits, sum credits, compare |
| `checkBalanceSheetEquation` | Assets, liabilities, equity | Boolean | A === L + E |
| `computeAccountChange` | Current balance, prior balance | Change amount | Subtraction |
| `computeCashFlowImpact` | Account type, change | Signed amount | Sign convention application |
| `aggregateToLineItem` | Accounts, mappings | Line item totals | Grouped summation |
| `computeSubtotal` | Child amounts | Subtotal | Summation |
| `reconciliationVariance` | GL balance, supporting balance | Variance | Subtraction (computed column in DB) |

All functions use `Decimal.js`. No native floating-point. No AI. No estimation.

## 11. COA Mapping — The Foundation

### Where Industry COAs Come From

| Source | What It Provides | Cost |
|---|---|---|
| XBRL US GAAP Taxonomy (FASB) | Canonical set of ~4,000 financial reporting concepts | Free download |
| SEC EDGAR XBRL Filings | Real company mappings — which XBRL tags each public company uses, filterable by SIC code | Free API |
| QuickBooks/Sage/Xero defaults | Industry-specific operational GL account templates | Free (create trial companies) |
| AICPA Audit Guides | Industry-specific recommended COAs | Paid (membership) |
| SBA/SCORE templates | Basic COA skeletons by industry | Free |

### Mapping Structure

```
Client GL Account (e.g., "4010-Product Revenue Domestic")
    ↓ maps to
Reporting Line Item (e.g., "Revenue from Contract with Customer")
    ↓ belongs to
Financial Statement Section (e.g., "Revenue" on Income Statement)
    ↓ tagged with
XBRL Tag (e.g., "us-gaap:RevenueFromContractWithCustomerExcludingAssessedTax")
    ↓ classified for
Cash Flow (e.g., "N/A — income statement account")
```

Each mapping is a one-time setup per client, refined over time. AI suggests initial mappings; humans approve. After approval, mappings are deterministic and versioned.

| Output | Dashboard of task status | Finished financial statements |

| Implementation | Weeks to months | Days (with AI-assisted mapping) |
| Price point | $30K–$500K+ | $25K–$75K |

### The Real Competitor

The real competitor is Excel. Most mid-market companies close their books in spreadsheets. They've never heard of BlackLine. The product replaces the manual process, not an incumbent tool.

### Go-to-Market

Sell to PE operating partners. One relationship, 10–20 portfolio company deployments. The PE firm's problem: "I need clean, trusted financials from all my portfolio companies, fast, every month." BlackLine is too expensive and heavy. FloQast is a workflow tool that still requires skilled controllers. This system produces the statements directly.

### Moat

- **Industry mapping library:** Every client enriches the templates. After 50 clients, onboarding is nearly instant.
- **Close benchmarking data:** System learns what "normal" looks like per industry and size.
- **PE network effect:** One PE firm deploys across portfolio. Auditors see the output and recommend to other clients. Second PE firm adopts. Compounding distribution.

---

## 15. What This System Cannot Claim

This system prevents structural and mechanical errors: wrong accounts, wrong amounts, unreconciled balances, missing entries, internal inconsistencies.

It does not prevent errors of judgment: wrong revenue recognition timing, incorrect asset impairment estimates, understated contingent liabilities. Those require human expertise and are validated by external auditors.

**Honest claim:** "We prevent the structural errors that account for a significant portion of restatements, and we surface the patterns associated with judgment-related issues for human review."

This is a large, real, and defensible value proposition.
